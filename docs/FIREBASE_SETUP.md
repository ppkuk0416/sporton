# SPORTON 경기별 실시간 댓글: Firebase 설정 및 출시 게이트

상태: 설계와 규칙 초안. 실제 Firebase 프로젝트 생성, 규칙 배포, 에뮬레이터 및 두 기기 시험, 공개는 완료되지 않았습니다. 설정 값만 넣어 자동 활성화하지 마세요.

## 방식과 책임
경기 상세에서 마지막 50개 댓글에 Firestore 웹 SDK의 실시간 리스너(onSnapshot)를 연결하고 화면을 벗어나면 해제합니다. 쓰기에는 Firebase Authentication 익명 사용자 인증과 Firestore 트랜잭션을 사용합니다. 웹소켓 서버를 직접 운영할 필요는 없습니다. 이는 Firestore SDK가 전송과 재연결을 관리한다는 뜻이며, 전송 프로토콜을 직접 선택하거나 항상 즉시 전달된다는 보장은 아닙니다. REST 주기 조회는 단순하지만 방문자마다 반복 요청을 만들어 실시간성과 비용의 절충이 커집니다. 별도 서버를 직접 운영하면 제어권은 크지만 연결·확장·장애 대응 운영이 필요합니다.

Firebase는 Google이 운영하는 클라우드 DB/Auth 서비스입니다. GitHub Pages에는 웹 파일만 두고 댓글 데이터는 Firebase에 저장합니다. 경기 점수는 기존 점수 API에서 가져오며 여기 저장하지 않습니다.

## 데이터 계약
- 경기 ID: 등록된 leagueId와 공급처 경기 ID를 '__'로 연결 (예: nba__123456789). 동일한 경기에서 여러 방문자가 같은 ID를 써야 하고 다른 리그는 충돌하지 않아야 합니다. 공급 ID는 실제 경기와 매칭해야 하며 클라이언트 ID 조작에 대한 검증은 이 규칙만으로 제공하지 않습니다.
- `matches/{matchId}/comments/{commentId}`: `uid`, `nickname`, `text`, `createdAt`. 시간은 serverTimestamp. id는 랜덤 자동 ID.
- `commentLocks/{uid}`: `lastPostedAt`, `matchId`, `commentId`. 댓글과 잠금 갱신을 하나의 트랜잭션으로 수행합니다.
- 규칙은 5초 간격 및 잠금과 댓글의 양방향 참조를 요구해 여러 댓글을 한 번에 작성하는 우회를 제한합니다. 자신이 작성한 댓글만 삭제 가능하고 편집은 금지합니다. 댓글 목록 조회는 limit 50 이하여야 합니다. 이 방식은 Firebase 사용자 ID별 제한이며 익명 계정 여러 개를 만드는 공격이나 분산 도배를 막지 못합니다.
- 기존에 쓰는 인증되지 않은 게시판·채팅 컬렉션에는 접근 권한을 주지 않습니다. 보안 규칙은 겹치는 allow가 하나라도 참이면 접근을 허용하므로 기존 프로젝트에 내용을 무작정 합치거나 덮어쓰지 마세요.

## 프로젝트 설정 (운영자)
1. 댓글 전용 Firebase 프로젝트 생성 또는 기존 프로젝트의 데이터/규칙 영향을 전문가가 확인합니다. Firestore 리전은 생성 후 변경이 어려우므로 비용·지연·법적 요구를 고려해 결정합니다.
2. Firestore 생성 시 기본 거부 규칙을 사용합니다. 테스트 모드로 공개하지 않습니다. Authentication에서 익명 로그인 활성화, 웹 앱 등록, 도메인 `sporton.live`와 실제 테스트 도메인을 검토합니다.
3. 공개용 웹 앱 설정은 사용자 식별 설정이며 서비스 계정 비밀키가 아닙니다. service-account 키나 관리자 인증정보는 사이트, GitHub, 브라우저 설정에 저장하거나 공유하지 않습니다. 웹 API 키의 요청 제한과 사용할 API 범위를 설정합니다. 웹 API 키 자체는 접근제어 수단이 아니므로 보안 규칙이 필수입니다.
4. 로컬 Firebase CLI와 Java, Emulator Suite를 준비하고 별도 테스트 프로젝트 ID로 규칙 에뮬레이터 시험을 통과시킵니다. 기존 프로젝트에 무심코 `firebase deploy --only firestore:rules`를 실행하면 기존 전체 규칙이 교체될 수 있습니다. 테스트·리뷰 후 별도 프로젝트에만 배포합니다.
5. 쓰기 제한을 완성합니다. 익명 계정 생성 남용에 대비해 App Check와 인증·쿼터를 실제 검증하고, 계정/네트워크 단위 추가 제한은 신뢰할 수 있는 서버에서 적용합니다. 신고·숨김·삭제 담당자와 정책, 문의 경로, 보관 및 삭제 주기, 개인정보 처리방침을 마련합니다. 단순 프론트 필터는 방어 수단이 아닙니다.
6. Firebase 사용량 경보 및 예산을 설정하고 실제 과금 정책·무료 할당량·상한 가능성을 검토합니다. 예산 알림은 자동으로 사용과 청구를 차단하지 않습니다. 리스너 최초 동기화와 변경, 재연결, 규칙의 문서 접근도 읽기 비용이 발생할 수 있습니다.
7. 독립된 두 기기에서 서로 다른 두 경기의 댓글 분리, 실시간 수신, 오프라인·재연결, 새로고침·재진입, 글 길이·악성 HTML, 5초 연속 쓰기와 한 번에 여러 댓글, 위조 UID·위조 시간·규칙 우회, 타인 삭제 거부, 본인 삭제, 리스너 해제를 검증합니다. 실패하면 공개하지 않습니다.
8. 운영 승인 후에만 동일한 공개 웹 앱 설정을 사이트에 넣고 배포하고, 실제 두 사용자로 운영 도메인을 검증합니다.
