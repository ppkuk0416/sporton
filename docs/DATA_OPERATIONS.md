# 경기 데이터 관리와 복구

## 데이터별 저장과 사용

| 데이터 | 조회 및 저장 | 범위와 한계 |
| --- | --- | --- |
| 해외 경기 | ESPN → 운영 점수 API. 장애 대비로 GitHub Actions가 `data/overseas/날짜.json`을 생성 | 화면은 API를 먼저 사용하고 실패 시 파일을 사용한다. 제공처의 이벤트 시각과 사이트가 확인한 시각은 다르다. |
| 국내 경기 | 네이버 스포츠 → 운영 점수 API, 별도 `data/domestic/날짜.json` | 제공처 사용 가능성과 정확도를 보장받지 못했다. 실패 시 리그별 마지막 정상 시각을 유지하고 stale로 표시한다. |
| 리그 순위 | 별도 `data/standings/리그.json` | 현재 축구 리그만 수집한다. 실패 시 이전 값과 원래 시각을 보존한다. |
| AI 분석 | 별도 AI 수집 파이프라인과 공개 `data/ai/snapshot.json` | 일부 공급 실패 시 이전 검증 자료를 유지한다. Actions 캐시·30일 아티팩트는 운영 DB나 장기 백업이 아니다. |
| 사용자 댓글 | Firebase 미연결 | 방문자 댓글을 영속 저장하지 않는다. 경기 데이터와 별도 데이터베이스가 필요하다. |

경기 파일은 현재 한국 시간 어제부터 6일 뒤까지 생성하며, 7일보다 오래된 날짜 파일은 현재 브랜치에서 정리한다. Git 이력은 남을 수 있으나 검색 가능한 장기 데이터베이스나 검증된 백업을 대신하지 않는다. 저장소 크기와 제공처 사용 조건을 확인하기 전 전체 경기·선수 기록을 무기한 축적하지 않는다.

## 장애 격리

국내 7개 리그가 전부 실패하면 수집 스크립트는 제어된 종료 코드 2를 반환한다. Actions는 해당 상황에서 정상 해외 자료와 보존된 국내 자료를 먼저 커밋한 다음 실패를 보고한다. Pages는 수집 작업 완료 후 현재 main의 검증을 통과한 파일만 게시한다. 예상치 못한 다른 오류는 커밋을 건너뛰고 실패한다. 하나의 공급 실패가 다른 공급의 정상 자료 게시를 막지 않게 하면서, 장애 알림을 성공으로 바꾸지 않는다.

개별 리그가 실패할 때 이전 정상 데이터가 있으면 원래 `fetchedAt`과 경기를 보존하고 `stale`로 표시한다. 이전 데이터가 없으면 빈 성공으로 위장하지 않고 `error`로 둔다. 미국 동부/UTC 날짜와 한국 날짜를 합치는 해외 수집은 원본 두 날짜 중 하나라도 누락되면 stale로 처리한다.

## 운영 점검

1. GitHub Actions의 Collect Korean scores, Score checks, Deploy score site, SPORTON production health 상태를 확인한다. 실패는 정확한 작업 로그와 리그를 확인한다. GitHub 알림을 실제로 받는지 소유자 설정은 별도 확인이 필요하다.
2. `node scripts/production-check.cjs`는 페이지·API·AI 갱신과 국내 7개 리그의 2분 이내 정상 응답을 각각 검사한다. 서버 health 200만으로 공급 정상이라고 판단하지 않는다. 임계치는 장애 감지 기준이며 데이터의 경기장 대비 지연을 보증하지 않는다.
3. 해외 공급 및 국내 공급, GitHub 저장을 각각 확인한다. 국내 오류 시 해외 파일의 원래 수집 시각과 경기 수, Pages 배포 여부를 확인하고 국내 오류를 숨기지 않는다.
4. 국내 복구 후에는 국내 경기 상세, 목록, 리그별 상태를 다시 확인한다. 공급에 계속 의존할 수 없는 경우 공식 제휴 API 또는 계약 제공처를 별도 검토한다.
5. 장애가 오래 지속될 때는 데이터 사용 권한, 비용·실제 갱신 지연, 보관 정책을 확인해 영속 DB와 백업을 설계한다. 적절한 보유기간이나 비용은 아직 확정되지 않았다.

## 팀·로고·전적 관리 기준

`data/teams/catalog.json`이 공급원·리그·팀 ID로 구분한 팀 정보 목록이다. 이름은 표시값이며 ID를 이름으로 대체하지 않는다. 같은 `10`이라도 KBL과 K리그를 합치지 않는다. 시즌 전적은 팀 키에 리그·공급처 시즌·그룹을 추가한 별도 기록이다. 최근 8일의 경기 결과를 시즌 전체 전적으로 계산하지 않는다.

- 팀마다 관측한 이름과 별칭, 최초·최근 관측 시각, 출처 파일과 SHA-256을 저장한다. 이름이나 로고가 바뀌면 최근 20건의 변경 근거를 남긴다. 이 목록은 전체 역사 데이터베이스나 영구 감사 로그가 아니다.
- 로고 URL의 출처와 실제 이미지 검증을 구분한다. 현재 `assetStatus: not-checked`이며, URL이 있다고 다운로드 성공이나 공식 사용 권한이 확인된 것은 아니다. 새 응답에서 로고가 누락되면 마지막으로 받은 로고와 그 원래 출처를 유지한다.
- 프런트의 로고 보완은 관리 목록에 등록된 정확한 팀 키만 사용한다. 팀 코드로 임의 URL을 만들거나 팀 이름만으로 다른 팀의 로고를 연결하지 않는다.
- 원본 데이터의 수집 시각인 `fetchedAt`, 실패를 재확인한 `lastAttemptAt`, 목록을 생성한 `generatedAt`을 구분한다. 재시도나 목록 재생성으로 원본이 최신이 된 것처럼 표시하지 않는다.
- 원본이 정리되거나 교체되어 현재 파일에서 근거를 재현할 수 없으면 과거 관측 자료로 취급한다. SHA-256은 파일 연결과 변경 탐지용이며, 공급처 기록의 실제 정확도에 대한 서명이나 보증은 아니다.

## 검증과 게시 차단

신규 수집은 누락·중복된 팀 ID, 리그/날짜 혼합, 같은 팀끼리의 경기, 잘못된 점수 상태, 미래 수집 시각을 정상 데이터로 게시하지 않는다. 실시간 API와 파일 수집에 같은 검증을 사용한다.

순위표는 팀 ID와 시즌을 보존하며 서로 다른 시즌을 한 표에 섞지 않는다. 경기 수와 승·무·패의 합, 득점·실점·득실차를 확인한다. 누락은 `null`로 남긴다. 공급처의 승점 감점이 있을 수 있어 `승점 = 승×3+무`를 강제하지 않으며, 순위가 없다고 배열 순서로 순위를 만들지 않는다.

새 순위표의 검증이 실패하면 마지막 정상 전적과 원래 수집 시각을 보존하고 `stale`로 표시한다. JSON은 같은 디렉터리의 임시 파일을 완성한 뒤 rename하여 파일 하나가 부분적으로 공개되지 않도록 저장한다. 여러 파일 전체에 대한 트랜잭션은 아니며, 최종 감사와 CI의 게시 차단이 함께 필요하다.

```sh
npm run data:sync  # 저장된 경기·전적을 검사하고 팀 목록을 갱신
npm run data:audit # 원본과 팀 목록의 식별자·수치·출처 해시 점검
```

전체 보고서는 무시 경로인 `.sporton/data-audit.json`에 기록한다. 원본 파일을 수동으로 변경한 경우 `data:sync` 후 `data:audit`를 실행한다. 변경 없는 원본으로 재실행하면 팀 목록을 다시 쓰지 않는다. 수집 작업은 끝에 목록을 동기화하고, Score checks와 Pages 배포는 감사를 통과해야 한다. 구조 오류는 종료 코드 1로 게시를 차단한다. 기존 자료의 ID 누락과 오래된 수집 시각은 경고로 구분하며, 이 호환 경로를 신규 수집의 정상 판정에 사용하지 않는다.

2026-10-31 점검에서는 28개 경기 파일의 경기 421건으로 281개 팀을 등록했다. 기존 순위표 161건은 공급처 팀 ID가 없어 검증 대기로 남겼으며, 관리 목록의 확정 전적과 연결하지 않았다. 화면에도 일부 팀 정보 확인 중임을 표시한다. 공급처에서 팀 ID를 포함해 재수집해야 이 상태를 해소할 수 있다. 현재 연결된 공개 API/CDN의 네트워크 접근과 실제 기록 정확도, 장기 DB·백업·원본 전체 보존은 별도 확인 사항이다.
