# 경기별 실시간 댓글: 설계 초안

상태: **구현 및 Firebase 프로젝트 연결 전**. 이 문서는 운영 기능이 아니다.

## 제품과 기술 선택

경기 상세에서 해당 경기의 댓글을 보고 작성한다. 경기 ID는 공급처 경기 ID만이 아니라 리그 ID와 함께 구성해 서로 다른 종목의 ID 충돌을 피한다. Firestore 문서 컬렉션은 `matches/{leagueId}__{providerId}/comments/{commentId}`이고, 댓글별 작성자 인증 ID, 닉네임, 내용, 서버 생성 시각을 저장한다. 경기나 리그의 ID 형식은 스포츠 레지스트리와 공급처별 검증 기준을 따라야 한다.

Cloud Firestore의 실시간 리스너를 사용한다. REST로 매번 조회하면 폴링 주기에 따른 지연과 빈 요청이 생기고, 직접 WebSocket 서버를 운영하면 접속 유지, 장애 복구, 확장, 저장을 별도로 관리해야 한다. Firestore는 실시간 구독과 저장을 제공하지만 네트워크·Firebase 장애 및 비용을 없애주지는 않는다. Firebase는 관리형 서비스이므로 별도 상시 데이터베이스 서버를 직접 운영할 필요는 없고 Google Cloud 프로젝트와 Firestore 데이터베이스는 반드시 필요하다.

## 접근과 안전

- 읽기는 경기 화면 진입 시 최근 댓글만 구독하고, 화면을 떠나거나 경기가 바뀌면 구독을 해제한다. 연결 실패와 지연, 전송 중 상태를 표시한다.
- 쓰기는 Firebase Authentication으로 식별하고 보안 규칙에서 작성자 UID, 필드 종류·길이·시각과 소유자 삭제 권한을 검증한다. 사용자 입력은 HTML로 실행하지 않는다.
- 동시 요청에서도 강제되는 서버 시간 기준 작성 간격을 검토한다. 구상은 `commentLocks/{uid}`와 댓글을 단일 트랜잭션으로 묶고 `getAfter`로 양쪽을 검증하는 방식이다. 에뮬레이터에서 우회 경로를 검증하기 전에는 안전하다고 주장하지 않는다.
- 익명 인증은 기기를 바꾸거나 저장 상태를 지우면 계정 복구가 어렵고, 여러 익명 계정 생성 자체를 막지 못한다. 스팸·비용 보호를 위해 App Check, 제한, 모니터링, 신고·삭제 운영을 검토한다.
- 기존 프로젝트의 다른 데이터가 있는 경우 보안 규칙을 덮어쓰지 않도록 별도 프로젝트 사용 또는 기존 규칙 병합 검토가 필요하다. 테스트 모드로 공개하지 않는다.

## 공개 전 완료 조건

1. 소유자가 관리하는 Firebase 프로젝트, Firestore 위치 및 비용 알림을 설정하고 웹 앱을 등록한다.
2. Authentication 로그인 방식과 도메인 설정을 완료한다.
3. 실제 보안 규칙을 배포하고 에뮬레이터에서 인증 없는 쓰기, 타인 삭제, 잘못된 필드, 우회·동시 요청을 거부하는지 검사한다.
4. 서로 다른 두 브라우저에서 같은 경기의 댓글 실시간 반영, 다른 경기 간 격리, 재접속, 권한 오류, 삭제를 확인한다.
5. 신고·차단·관리자 삭제 절차, 개인정보 안내, 보관 및 비용 관리 책임을 정한다.
6. 사이트에 공개 설정을 연결한 후 운영 도메인에서 확인한다. 실제 Firebase 연결 전에는 댓글을 활성화하지 않는다.

Firestore의 리스너 읽기 및 쓰기에는 사용량에 따른 비용이 발생한다. 무료 할당량과 비용은 실제 프로젝트 설정과 지역을 기준으로 확인한다.
